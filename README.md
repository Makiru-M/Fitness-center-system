**«FitnessClub IS»** — виробничо орієнтована багаторівнева інформаційна система комплексної автоматизації операційної діяльності, клієнтського сервісу, кадрового обліку та бізнес-аналітики сучасного спортивно-оздоровчого клубу. Проєкт розроблено в рамках курсового проєкту з дисципліни **«Проектування інформаційних систем»** для спеціальності **126 «Інформаційні системи та технології»**.

Система забезпечує наскрізну автоматизацію **39 бізнес-задач** за технічним завданням [`IS structure.md`](file:///E:/%D0%9D%D0%B0%D0%B2%D1%87%D0%B0%D0%BD%D0%BD%D1%8F/3%20%D0%BA%D1%83%D1%80%D1%81/%D0%91%D0%B0%D0%B7%D0%B8%20%D0%B4%D0%B0%D0%BD%D0%B8%D1%85/IS%20structure.md) із суворою ізоляцією прав доступу на рівні сесій ядра PostgreSQL, динамічними пулами з'єднань per-user на чистому JDBC та сучасним клієнтським SPA-інтерфейсом, який взаємодіє виключно через REST API.

## 🏛 Архітектурний стек та ключові принципи

```
┌────────────────────────────────────────────────────────────────────────┐
│                   КЛІЄНТСЬКИЙ РІВЕНЬ (Frontend SPA)                    │
│  Vanilla ES6 Modules (Zero-Bundler) • 100% REST API • Fallback View    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ HTTP / JSON (порт 8080)
┌───────────────────────────────────▼────────────────────────────────────┐
│                    СЕРВЕРНИЙ РІВЕНЬ (Spring Boot 3.4.3)                │
│  Java 21 • Pure JDBC (JdbcTemplate) • DynamicRoutingDataSource         │
│  HikariCP Per-User Pools • No JPA / No Hibernate • REST Controllers   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Native PostgreSQL Connection (порт 5544)
┌───────────────────────────────────▼────────────────────────────────────┐
│                      РІВЕНЬ ДАНИХ (PostgreSQL 16)                      │
│  Схема 3НФ / НФБК • 6 системних ролей RBAC • 11 RLS-політик безпеки   │
│  Процедури SECURITY DEFINER • Віконні функції • Аудиторські тригери   │
└────────────────────────────────────────────────────────────────────────┘
```

### 1. Рівень даних: PostgreSQL 16
* **Нормалізація:** Реляційна модель проєкту декомпонована до **третьої нормальної форми (3НФ)** та **нормальної форми Бойса-Кодда (НФБК)** без надлишковості й аномалій модифікації (див. обґрунтування в [`DB_Implementation_Summary.md`](file:///E:/%D0%9D%D0%B0%D0%B2%D1%87%D0%B0%D0%BD%D0%BD%D1%8F/3%20%D0%BA%D1%83%D1%80%D1%81/%D0%91%D0%B0%D0%B7%D0%B8%20%D0%B4%D0%B0%D0%BD%D0%B8%D1%85/docs/DB_Implementation_Summary.md)).
* **Рольова модель (RBAC):** Створено 6 ізольованих системних ролей СУБД (`club_guest`, `club_client`, `club_manager`, `club_coach`, `club_admin`, `club_director`), кожна з мінімально необхідним набором привілеїв `GRANT / REVOKE`.
* **Безпека рядкового рівня (Row-Level Security — RLS):** На ключових таблицях функціонують **11 RLS-політик**, що гарантують фізичну ізоляцію даних на рівні рядків ядра СУБД (клієнт бачить лише власний профіль, абонементи та записи; тренер — власні заняття та медичні застереження закріплених підопічних).
* **Інкапсуляція бізнес-транзакцій:** Критичні багатотабличні операції (реєстрація клієнта з оформленням абонемента, перерахунок заморозки, аудит) реалізовані збереженими функціями `SECURITY DEFINER`.
* **Аналітика на чистому SQL:** Комплексні звіти D1–D6 побудовані на базі віконних функцій (`SUM() OVER()`, `DENSE_RANK()`, `AVG() OVER()`) за методикою конспекту проф. Малахова Є.В.

### 2. Серверний рівень: Spring Boot 3.4.3 (Java 21)
* **Абсолютна відмова від ORM/Hibernate:** Вся взаємодія з БД реалізована виключно через низькорівневий `JdbcTemplate` та параметризовані SQL-запити із суворим захистом від SQL-ін'єкцій.
* **Динамічна per-user автентифікація в СУБД:** Замість спільного суперкористувацького з'єднання реалізовано компонент `DynamicRoutingDataSource` на базі динамічних пулів HikariCP (`UserConnectionPoolService`). Кожен запит користувача виконується від імені його персонального логіна СУБД, завдяки чому RLS-політики та права доступу застосовуються безпосередньо ядром PostgreSQL.
* **REST API архітектура:** Чітко структуровані контролери розділені за підсистемами (`GuestController`, `ClientController`, `ManagerController`, `CoachController`, `HrController`, `DirectorController`).

### 3. Клієнтський рівень: Модульний Vanilla ES6 SPA
* **Zero-Bundler модульність:** Інтерфейс реалізовано у вигляді модульного односторінкового застосунку (SPA) на чистих веб-стандартах ES6 (`<script type="module">`, класи, async/await) без важких фреймворків, збирачів (Webpack/Vite) чи транспіляторів.
* **100% REST API клієнт (Відсутність Mock-режиму):** Усі операції та рендеринг сторінок здійснюються виключно через реальні HTTP-запити до бекенду. Заглушковий Mock-режим повністю демонтовано для забезпечення чистоти експерименту й цілісності бізнес-логіки.
* **Інтерактивний моніторинг зв'язку:** У верхній панелі навігації інтегровано живий індикатор статусу підключення до сервера (`API: Онлайн` / `API: Офлайн`).
* **Захисний екран недоступності сервера (Fallback View):** При зупинці бекенду або обриві мережі SPA не падає з помилкою, а автоматично приховує робочі секції й відображає ергономічний екран «Сервер тимчасово недоступний» з поточною цільовою адресою та кнопкою «Повторити спробу». Після підняття бекенду клієнт натисканням однієї кнопки без перезавантаження сторінки повертається до свого активного робочого екрана.

## 🎯 Охоплення бізнес-задач за ТЗ (39 задач)

Згідно з технічним завданням курсового проєкту [`IS structure.md`](file:///E:/%D0%9D%D0%B0%D0%B2%D1%87%D0%B0%D0%BD%D0%BD%D1%8F/3%20%D0%BA%D1%83%D1%80%D1%81/%D0%91%D0%B0%D0%B7%D0%B8%20%D0%B4%D0%B0%D0%BD%D0%B8%D1%85/IS%20structure.md), система повністю реалізує 39 задач, розподілених між 6 ролями:

### 👤 1. Гість клубу (Guest) — 4 задачі
* **G1:** Онлайн-реєстрація гостя з автоматичним створенням картки клієнта, облікового запису та оформленням обраного абонемента.
* **G2:** Публічний рейтинг та популярність тренерського складу (з фільтрацією за напрямками).
* **G3:** Перегляд актуального публічного прайс-листа послуг та типів абонементів.
* **G4:** Перегляд каталогу залів клубу, їх місткості та характеристик оснащення.

### 🏋️ 2. Клієнт клубу (Client) — 6 задач
* **Cl1:** Перегляд та редагування персональних контактних даних у профілі.
* **Cl2:** Купівля та продовження абонемента (з підтримкою перевірки промокодів).
* **Cl3:** Заморозка активного абонемента з автоматичним зміщенням дати його закінчення.
* **Cl4:** Онлайн-запис на групові тренування з урахуванням лімітів місткості залів.
* **Cl5:** Онлайн-запис на індивідуальні тренування до персонального тренера.
* **Cl6:** Скасування попереднього запису на тренування згідно з регламентом клубу.

### 📋 3. Менеджер по роботі з клієнтами (Manager) — 8 задач
* **M1:** Оформлення нового клієнта у рецепції фітнес-клубу.
* **M2:** Повний пошук та модифікація картки клієнта (включаючи медичні обмеження).
* **M3:** Продаж та пролонгація абонементів клієнтам на рецепції.
* **M4:** Електронний Check-in відвідування (контроль турнікета, перевірка чинності абонемента).
* **M5:** Ручний запис клієнта на групове заняття адміністратором.
* **M6:** Запис клієнта на персональне заняття до обраного тренера.
* **M7:** Оформлення заморозки абонемента за заявою відвідувача.
* **M8:** Скасування або перенесення тренувань клієнта через адміністративну панель.

### 👥 4. HR-відділ / Менеджер персоналу (HR Manager) — 6 задач
* **HR1:** Прийом на роботу нового тренера (створення профілю та системного облікового запису).
* **HR2:** Редагування даних тренера (кваліфікація, контакти, спеціалізація).
* **HR3:** Звільнення тренера (переведення в архівний статус, блокування облікового запису).
* **HR4:** Прийом на роботу менеджера рецепції.
* **HR5:** Редагування даних співробітника операційного штату.
* **HR6:** Звільнення менеджера (блокування доступу до СУБД та операцій).

### 🥋 5. Тренер (Coach) — 5 задач
* **C1:** Перегляд розкладу власних індивідуальних і групових занять.
* **C2:** Отримання відомості запису клієнтів на тренування (з медичними примітками).
* **C3:** Фіксація проведення персонального тренування або відмітки про неявку клієнта.
* **C4:** Фіксація проведення групового заняття з підрахунком фактичної кількості відвідувачів.
* **C5:** Формування запиту адміністрації на скасування чи перенесення заняття.

### 📊 6. Керівник / Директор (Director) — 12 задач
* **D1:** Аналітичний звіт щодо виручки (динаміка за період, послуги, внесок менеджерів).
* **D2:** Звіт з відвідуваності залів та динаміки унікальних візитів клієнтів.
* **D3:** Звіт ефективності та популярності тренерів (заповнюваність груп, обсяг тренувань).
* **D4:** Моніторинг завантаженості залів за днями тижня та годинами пік.
* **D5:** Виявлення проблемних зон (прострочені абонементи, систематичні неявки).
* **D6:** Журнал безпеки та аудиту дій (Audit Log модифікацій сутностей).
* **D7:** Конфігуратор нових типів абонементів клубу.
* **D8:** Введення залів в експлуатацію та налаштування їхньої місткості.
* **D9:** Створення та управління маркетинговими промокодами зі знижками.
* **D10:** Публікація та оновлення тарифів прайс-листа.
* **D11:** Формування щотижневого шаблону розкладу групових занять.
* **D12:** Налаштування слотів доступності тренерів для персональних тренувань.

## 🚀 Покрокова інструкція «Як працювати з проєктом»

Для роботи системи потрібні:
* **Docker Desktop** (або локально встановлений PostgreSQL 16)
* **Java Development Kit (JDK) 21**
* **Apache Maven 3.9+**
* Сучасний веб-браузер (Chrome, Firefox, Edge)

### Крок 1. Запуск бази даних PostgreSQL 16
Проєкт налаштовано на роботу через Docker-контейнер з нестандартним портом `5544` (щоб уникнути конфлікту зі стандартним локальним портом `5432`).

1. У корені проєкту підніміть контейнер PostgreSQL:
   ```bash
   docker-compose up -d
   ```
2. Виконайте первинну ініціалізацію або скидання БД до еталонного стану в один клік:
   * **PowerShell (рекомендовано):**
     ```powershell
     .\restore_db.ps1
     ```
   * **Windows CMD:**
     ```cmd
     restore_db.bat
     ```
   * *Або прямим викликом psql:*
     ```bash
     psql -h localhost -p 5544 -U postgres -d fitness_center_db -f fitness_schema_and_roles.sql
     ```

### Крок 2. Запуск серверної частини (Spring Boot)
1. Перейдіть до каталогу бекенду:
   ```bash
   cd backend
   ```
2. Запустіть сервіс через Maven:
   ```bash
   mvn spring-boot:run
   ```
3. Сервер скомпілює проєкт, ініціалізує системні пули з'єднань HikariCP та запуститься на:
   * **Базова адреса застосунку:** `http://localhost:8080/`
   * **Корінь REST API:** `http://localhost:8080/api`
   * **Health-check ендпоінт:** `http://localhost:8080/api/health`

### Крок 3. Робота в інтерфейсі користувача
1. Відкрийте веб-браузер і перейдіть за адресою:
   **[http://localhost:8080/](http://localhost:8080/)**
   *(Фронтенд віддається безпосередньо статичним веб-сервером Spring Boot)*.
2. **Індикатор зв'язку API:**
   * Зверху праворуч відображається живий статус з'єднання:
     - Зелений бейдж: `API: Онлайн` — бекенд доступний, запити успішно обробляються.
     - Червоний бейдж: `API: Офлайн` — з'єднання втрачено.
3. **Захисний екран недоступності сервера:**
   * Якщо бекенд зупинено або мережа недоступна, інтерфейс автоматично приховує робочі екрани й виводить захисний банер із зазначенням URL бекенду та кнопкою **«Повторити спробу»**. Після рестарту сервера натисніть її, і застосунок миттєво відновить роботу без втрати сесії.
4. **Швидка авторизація (Quick Login):**
   * Для зручності тестування в модальному вікні входу та у верхній панелі розміщено кнопки швидкого перемикання між усіма 6 тестовими ролями системи.

> [!IMPORTANT]
> **Пряме відкриття `frontend/index.html` локально через протокол `file:///` не підтримується!** Сучасні веб-браузери блокують модулі ES6 (`type="module"`) при відкритті з файлової системи через політику безпеки CORS. Застосунок повинен відкриватися виключно через HTTP-сервер за адресою `http://localhost:8080/`.

## 🔄 Еталонне відновлення БД (Reset / Rollback)

Для забезпечення повторюваності black-box та regression тестів у репозиторії створено повний еталонний дамп початкового стану [`backup_initial_state.sql`](file:///E:/%D0%9D%D0%B0%D0%B2%D1%87%D0%B0%D0%BD%D0%BD%D1%8F/3%20%D0%BA%D1%83%D1%80%D1%81/%D0%91%D0%B0%D0%B7%D0%B8%20%D0%B4%D0%B0%D0%BD%D0%B8%D1%85/backup_initial_state.sql) та швидкі сценарії автоматичного відновлення:

* **Через PowerShell:**
  ```powershell
  .\restore_db.ps1
  ```
* **Через Windows CMD або подвійний клік у Провіднику:**
  ```cmd
  restore_db.bat
  ```

> [!NOTE]
> Скрипт примусово скидає всі активні з'єднання з базою `fitness_center_db` через `pg_terminate_backend`, повністю перестворює базу даних, налаштовує 6 ролей СУБД, RLS-політики та наповнює схему еталонними тестовими даними менш ніж за **2 секунди**.
